# 阶段三 性能分析：Baseline 组合指令 vs vdot 指令族（INT8 / INT4 / 三值）

> **口径声明（必读）**
> 本文的性能数字分为两类，混用即视为错误：
> 1. **实测（Measured）**：① vdot 单元级吞吐/延迟（Verilator 单元仿真，3 cycle / 1.0 inst/cycle）；② **香山昆明湖 V2 emu 上的整程序 cycleCnt**（§6.3），用于给出实测加速比。
> 2. **解析估算（Estimated）**：§2–§4 按 vdot 的 **K=8** 语义建模（8 个 int8 lane），未在香山或 NEMU 上逐条运行；§6.3 的 emu 内核则是 **VLMAX=16** 的 RVV 基线（含 2× lane 工作量），两者口径见 §6.4。
>
> 加速比结论以 §6.3 实测值为准；§3/§4 的估算区间仅保留为建模参考。
>
> **环境提示（2026-11-10 更新）**：主机已具备 RISC-V 工具链、香山源码、emu 与 **yosys 0.52**（`.tools/yosys`，deb 解包）。§5 已改为三模式实跑综合结果，历史单模式日志保留为对照。

| 项 | 内容 |
|---|---|

## 1. 基线定义（RISC-V 已有向量指令组合）

```asm
# int8 → int32 加宽，逐元素乘，再归约求和；结果与 vdot.vv 等价
vsetvli    t0, x0, e8, m1
vsext.vf2  v4, v1            # e8(f0.5) -> e16(m1)，只处理 K=8 个 lane
vsext.vf2  v6, v2
vsetvli    t0, x0, e32, m2
vsext.vf2  v8,  v4           # e16(m1) -> e32(m2)
vsext.vf2  v12, v6
vmul.vv    v16, v8, v12      # e32m2 逐元素乘
vsetvli    t0, x0, e32, m1
vredsum.vs v3, v16, v0       # 32 bit 求和（v0 预清零）
vmv.x.s    t1, v3
```

**为什么必须加宽到 32 bit**：`vredsum.vs` 的累加宽度等于目标 SEW，若停在 e16 则 8 项和在 `+131072` 处溢出（与 `ipd/01` §2.4 同一边界）。因此基线必须走 int8→int16→int32 两级加宽，这是它指令数偏多的直接原因。

**等价性验证**：`tests/ref_baseline.py` 在元素粒度模拟上述序列，对 1518 条向量中的 1513 条写回用例逐一比对，全部与 vdot 期望一致（`RESULT: PASS`）。这证明"基线确实算出同一个结果"，是性能对比有意义的前提。

> 已复核：`vsext.vf2` 的 EMUL 约束（源 e8 f0.5→e16m1、源 e16m1→e32m2）与 `vredsum.vs` 的 vd/vs2 宽度语义已在 NEMU 上跑通同一序列（`docs/phase3/03_baseline_nemu.log`，1513/1513），该项闭环。实际执行序列见 `tests/run_nemu_baseline.py`。

## 2. 工作量与 uop 数

本节按 vdot 的 **K=8** 语义建模。假设 128 bit 数据通路：m1 = 1 beat、m2 = 2 beats；每 beat 1 uop。

| 指令 | SEW/LMUL | 数量 | 每指令 uop | 小计 uop |
|---|---|---|---|---|
| `vsext.vf2`（e8 f0.5→e16m1） | 8→16 / m1 | 2 | 1 | 2 |
| `vsext.vf2`（e16m1→e32m2） | 16→32 / m2 | 2 | 2 | 4 |
| `vmul.vv`（e32m2） | 32 / m2 | 1 | 2 | 2 |
| `vredsum.vs`（e32m2） | 32 / m2 | 1 | 2 | 2 |
| **基线合计** | | **6** | | **10** |
| `vdot.vv` | 8 / m1 | **1** | **1** | **1** |

| 指标 | 基线（8-lane，估） | vdot（实测/结构性） | 比值 |
|---|---|---|---|
| 计算指令数 | 6 | 1 | **6 : 1** |
| 含 vtype 切换的总指令数 | 9（+3 `vsetvli`） | 1（通常复用已设 vtype） | **9 : 1** |
| 向量 uop 数 | 10 | 1 | **10 : 1** |
| 写回带宽（每点积） | 6×128 bit + 标量 | 1×128 bit | **≈6 : 1** |
| 中间寄存器占用 | m1×2 + m2×3 | 无 | — |

> 若把基线写成"整寄存器 16 lane"（§6 的 emu 内核就是这种写法），则为 m2/m4 口径、20 uop；那相当于做 2× 的 lane 工作量，不能直接与 8-lane 的 vdot 比。§6.4 给出对应口径说明。

## 3. 延迟模型（单次点积，估算）

依赖链为 `vsext → vsext → vmul → vredsum`（vs1 与 vs2 两条支路并行）。

```
lat ≈ Σ_{链上各指令} (uop 数 + L_pipe) + vtype 切换开销
    = (1 + 2 + 2 + 2) + 4 × L_pipe + Δvtype
```

| 参数 | 保守取值 | 说明 |
|---|---|---|
| `L_pipe` | 2–3 cycle | 单 uop 流水延迟假设，需用既有 `VAlu` 实测替换 |
| `Σ uop` | 7 | 链上 4 条指令的 beat 数（8-lane 口径） |
| `Δvtype` | 0–3 cycle | 3 次 `vsetvli` 的重配置开销，取决于实现 |

| 场景 | 基线延迟（估） | vdot 延迟（实测） | 估算加速比 |
|---|---|---|---|
| 乐观（L=2，Δvtype=0） | 15 cycle | 3 cycle | **≈5.0×** |
| 保守（L=3，Δvtype=3） | 22 cycle | 3 cycle | **≈7.3×** |

> 结论口径：**单次点积的延迟加速比估算区间约 5–7×**（8-lane 基线）。`3 cycle` 是实测值，基线侧两个数字是估算，区间宽度来自 `L_pipe` 与 `vsetvli` 开销的不确定性。若按 16-lane 基线（§6 内核），链上 uop 翻倍，估算约 7–12×，但那是 2× 工作量口径。

## 4. 吞吐模型（批量点积，估算）

在向量发射端口 1 uop/cycle 的持续带宽下：

| 项 | 基线 | vdot |
|---|---|---|
| 每个 8 元素点积占用的发射槽 | 10 | 1 |
| 持续吞吐（上限） | 1/10 点积/cycle | 1 点积/cycle |
| 比值 | — | **≈10×（发射受限上限）** |

实际可持续吞吐还受：向量寄存器读端口（vdot 每周期读 2×128 bit）、写回端口（每周期 1×128 bit）、以及 vdot 与其它向量指令争用发射端口的影响。因此**工程预期取 5–10×**，而不是 10× 的上限。16-lane 基线的对应上限为 20×，但工作量不同，不可直接对比。

**为什么 vdot 能到 1 条/周期**：乘法在 EX1、加法树在 EX2，两级各有独立硬件，不共享乘法器，也无跨 uop 归约；实测背靠背 1024 条无气泡（测试报告 §5）。

## 6. 实测（香山昆明湖 V2 emu）

### 6.1 测量方法与口径

在香山 `emu`（Verilator 5.034，`DefaultConfig`（昆明湖 V2 基线），VLEN=128）上运行 4 个自检汇编内核
（`tests/phase2/xs_emu/vdot_perf.S`），取 `HIT GOOD TRAP` 时的 `cycleCnt`：

```
per_iter(k) = (C_k - C_empty) / NITER
speedup     = per_iter(baseline) / per_iter(vdot)
```

`NITER = 2000`（内核默认 20000 的 1/10，用于把单次 emu 运行压缩到分钟级；这是线性除法，不改变比值）。
`tests/phase2/xs_emu/build.sh` 现显式传入 `-DPERF_NITER=${PERF_NITER:-2000}`，保证重建产物与本报告口径一致
（此前脚本未固定该宏，重建内核会退化为 20000，已修正）。
四个内核全部在 difftest 下输出 `PERF result=OK` 并 `HIT GOOD TRAP`，日志见
`docs/phase2/logs/xs_emu_perf_{empty,vdot,rvv,scalar}.log`；NEMU 独立复跑的同一批内核
见 `docs/phase2/logs/nemu_standalone_perf_*.log`（每点积退休数与上表一致）。
**重复测量（G5）**：每个内核独立跑 3 次，12/12 次 `PERF result=OK` 且 `HIT GOOD TRAP`，
cycleCnt 完全一致，汇总见 `docs/phase3/05_perf_repeat.log`（原始日志在 `build/emu_repeat/`，未入库）。

### 6.2 原始数据

| 内核 | 每轮做的工作 | instrCnt | cycleCnt | per-iter (cyc) |
|---|---|---|---|---|
| `perf_empty` | 仅循环（`addi`+`bne`） | 4,118 | 11,108 | —（基准） |
| `perf_vdot` | 1 × `vdot.vv` | 6,118 | 12,123 | **0.51** |
| `perf_rvv` | `vwmul.vv` + `vwredsum.vs` | 8,119 | 23,109 | **6.00** |
| `perf_scalar` | 8 × `mul` + 8 × `add`（int32） | 38,135 | 21,022 | **4.96** |

### 6.3 结果

| 指标 | 标量基线 | RVV 基线 | vdot |
|---|---|---|---|
| 每轮周期（扣除空循环） | 4.96 | 6.00 | 0.51 |
| 相对标量加速比 | 1.0× | 0.83× | **9.8×** |
| 相对 RVV 基线加速比 | 1.2× | 1.0× | **11.8×** |
| 退休指令 / 点积 | 17 | 2 | 1 |
| 向量指令 / 点积 | — | 2 | 1 |
| 参与运算的 lane 数 / 点积 | 8 | 16（含 8 个 0 填充） | 8 |

解读：

1. vdot 的系统级稳态吞吐为 **1 条/cycle**：2000 条 vdot 只增加 1,015 个周期，循环体的
   `addi`+`bne` 与向量发射重叠，和单元级 1.0 inst/cycle 一致。
2. 标量基线 17 条退休指令（16 条 `mul`/`add` + 1 条累加器清零）/ 4.96 周期 ≈ 3.4 IPC，
   已较充分利用乱序后端；标量恰好做 8 个乘积，9.8× 是 **lane 公平** 的实测值。
3. RVV 基线（`vwredsum` 对 `vd` 的串行依赖）比标量慢约 21%（6.00 vs 4.96 cycle/点积）。
   注意它在 VLMAX=16 下做 16 lane（8 lane 为 0 填充），相当于 vdot 的 2× 工作量；
   因此 **11.8× 是上界，不是 lane 归一后的公平值**，详见 §6.4。
4. **局限**：emu 是功能级仿真，周期数包含取指/发射/乱序窗口等微架构行为，
   但不含真实存储层次与物理频率；因此**横向比值可信，绝对值不可外推**。
   复测请用 §6.1 的同一脚本与同一 NITER，避免混用不同编译路径。
5. **重复测量（G5，已完成 2026-11-04）**：每个内核独立运行 3 次，cycleCnt 与中位数如下，
   四次点极差均为 **0**（0.00%，判据 <5%）；12/12 次 `PERF result=OK` 且 `HIT GOOD TRAP`。
   因此本表数值是统计稳定的，但仍仅限"本 emu 配置 + 本二进制 + NITER=2000"。

   | 内核 | 3 次 cycleCnt | 中位数 | 极差 | 极差% |
   |---|---|---|---|---|
   | empty | 11,108 / 11,108 / 11,108 | 11,108 | 0 | 0.00% |
   | vdot | 12,123 / 12,123 / 12,123 | 12,123 | 0 | 0.00% |
   | rvv | 23,109 / 23,109 / 23,109 | 23,109 | 0 | 0.00% |
   | scalar | 21,022 / 21,022 / 21,022 | 21,022 | 0 | 0.00% |

   零离散说明 emu 周期数在固定二进制/固定 seed 下是确定性的，它证明**测量可复现**，
   不等于跨主机、跨配置的稳定性；证据见 `docs/phase3/05_perf_repeat.log`。

### 6.4 公平性口径（RVV 基线的 lane 数）

`perf_rvv` 内核沿用 `vsetvli e8,m1` 的 VLMAX=16，`vwmul.vv`/`vwredsum.vs` 对 16 个 lane
做乘加（数据区后 8 字节为 0），而 `vdot.vv` 的规范只做 K=8。因此 RVV 基线在 RTL 上做了
约 **2×** 的 lane 工作量，11.8× 只能作为**上界**引用。

为什么没有直接把该内核改成 `vl=8`：香山 NEMU（a683e0b）的 `reduction_instr` 在宽归约
（`vwredsum`）时按 `vtype->vsew`（窄宽度）读取 `vs2`，而不是 `vsew+1`。对本文的 8 个
正乘积，实测 `vl=4/8/16` 分别得到 `22/60/120`，即只累加了 `vl/2` 个元素；`vl=8` 时
RTL 正确求和 120 而 NEMU 参考给出 60，difftest 直接失败。该缺陷属于 NEMU 参考模型，
不在 vdot 补丁范围；修它会影响其它 RVV 指令的 difftest，故本阶段不动。

结论：
- **9.8×（对标量）** 是 lane 公平的实测值，作为主结论引用。
- **11.8×（对 RVV）** 是 16-lane 基线的实测上界；若要给 lane 归一值，需要先修 NEMU
  宽归约缺陷（或用不同指令序列重建基线）并重跑 emu，列入 `ipd/04` G5。

## 6.5 三模式单元级吞吐与批量收益

> 口径：本节的三模式数字是**单元级实测**（Verilator，`docs/phase2/logs/03_unit_test.log`）+ **结构性推算**；系统级 emu 仅实测了 INT8（§6）。INT4/三值的整程序加速比尚未在 emu 上重跑，不得当作实测值引用。

| 模式 | 每指令 lane | 每指令乘累加 | 延迟 | 吞吐（实测） | 每周期乘累加 |
|---|---|---|---|---|---|
| `vdot.vv`（INT8） | 8 | 8 | 3 cycle | 1 inst/cycle | 8 |
| `vdot4x2.vv`（INT4） | 16 nibble | 16 | 3 cycle | 1 inst/cycle | **16** |
| `vtdot.vv`（三值） | 16 | 16（选择/取反） | 3 cycle | 1 inst/cycle | **16（乘 0 个乘法器）** |

相对 INT8 基线：

| 维度 | INT8 | INT4X2 | VTDOT | 说明 |
|---|---|---|---|---|
| 每指令 MAC | 8 | 16 | 16 | 2× 吞吐 |
| 源数据位宽 | 2×128 bit | 2×128 bit | 2×128 bit | 读口不变 |
| 权重存储 / 16 个 | 128 bit（int8） | 64 bit（int4） | **32 bit（2-bit 码）** | 三值相对 INT8 4× 压缩 |
| EX1 乘法器 | 8×8×8 | 16×4×4 | **0** | BitNet 路径无乘法器 |
| EX2 归约树 | 1×20-bit | 2×12-bit（共享） | 2×12-bit（共享） | 不为三值新增归约网络 |
| 结果 | 1×32 bit | 2×32 bit | 2×32 bit | 双结果双累加流 |

批量收益的结构性判断：

1. **寄存器带宽**：一条指令消费 32 bit 三值权重而不是 128 bit INT8 权重，权重侧的数据搬运量降到 1/4；在权重受限的 GEMV 中，这是比 MAC 数更直接的收益。
2. **发射槽**：三模式都是 1 uop/指令。INT4 与三值把每指令 MAC 翻倍，等价于把发射压力减半。
3. **面积**：三值 EX1 只是取反 + 三选一，逻辑深度低于 `4×4` 乘法器；但当前 RTL 三模式并行展开，总面积为三条 EX1 之和（未分时复用），需综合后给出准确值。

> 对 BitNet 线性层的建议口径：`vtdot.vv` 的价值 = "16 MAC/指令 + 权重 4× 压缩 + 零乘法器"，不要把它与 INT8 的 9.8× 标量加速比直接相乘；后者是不同负载、不同 lane 数的实测值。

## 7. 风险与偏差

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| P-1 | 基线序列在 NEMU 上语义未验证（EMUL/vredsum 细节） | 基线延迟估算可能失真 | **已关闭**：1513/1513 语义等价 + emu 上 `perf_rvv`/`perf_scalar` 均 difftest 通过 |
| P-2 | `L_pipe` 用经验值 | 延迟加速比区间偏宽 | **已关闭**：加速比改用 §6.3 整程序实测 |
| P-3 | 未考虑内存/取指瓶颈 | 批处理收益被低估/高估 | 内核只做寄存器运算，未含数据搬运；如需存储受限结论需另建内核 |
| P-4 | 未综合 | 面积数字不可引用 | 保持"估算"标注（U-05） |
| P-5 | vdot 与其它向量指令争用发射端口 | 实际上限低于 10× | 用 P5 混合负载给出更真实的收益 |
| P-6 | RVV 基线与 vdot 的 lane 数不同（16 vs 8） | 11.8× 高估 | **已标注**：11.8× 仅为上界；主结论用 lane 公平的 9.8×，lane 归一值待 G5 |

## 8. 结论

1. **功能层面**：基线组合指令与 `vdot.vv` 结果等价（1513/1513 用例），性能对比成立。
2. **指令/uop 层面**：8-lane 基线 6 条计算指令 / 10 个向量 uop，vdot 1 条 / 1 个 uop，
   减少 6×（指令）与 10×（uop）；16-lane 基线为 20 uop，对应比值 20× 但工作量翻倍。
3. **实测加速比（香山 emu，§6.3）**：vdot 0.51 cycle/点积，标量基线 4.96、RVV 基线 6.00，
   即 **对标量 9.8×（lane 公平）、对 16-lane RVV 基线 11.8×（上界）**；vdot 系统级吞吐 1 条/cycle。
4. **单元级**：3 cycle 延迟、1.0 inst/cycle 吞吐（Verilator 单元仿真），与系统级一致。
5. **三模式扩展**：`vdot4x2.vv` 与 `vtdot.vv` 把每指令乘累加从 8 提升到 16，三模式单元级吞吐均为 1 inst/cycle；BitNet 路径零乘法器、权重存储相对 INT8 压缩 4×（§6.5，结构性推算，系统级未重跑）。
6. **诚实边界**：§3/§4 的延迟/uop 解析模型仍是估算，仅作建模参考；对外引用加速比应使用
   §6.3 的实测值，并注明"香山昆明湖 V2 emu（Verilator 功能级仿真，NITER=2000）"，
   不得外推为真实频率下的绝对性能。U-04 已按此关闭。
